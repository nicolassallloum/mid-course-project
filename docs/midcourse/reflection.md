# Reflection

I used AI as a planning, coding, test-generation, and debugging partner during this sprint, but I kept the repository, the course constraints, and the verification evidence as the source of truth. For design work, I used structured prompts to break the two features into model, storage, API, test, and frontend steps. For implementation, I asked for focused changes to specific files rather than requesting a full project rewrite. For testing, I used AI to brainstorm edge cases and draft named pytest tests, then reviewed whether each test actually represented the acceptance criteria.

The most helpful moment was the combined-filter test design. The AI quickly suggested title search, description search, no-match behavior, and enum validation. That saved time, but I changed the setup so status changes occurred through the real PATCH endpoint and valid transition sequence. This made the tests better aligned with the existing backend rules instead of creating unrealistic state directly.

The AI slowed me down when its first due-date proposal treated every past due date as overdue. That looked reasonable at first, but it would mark completed tasks as currently actionable failures. My review changed the rule to exclude `Done` tasks, and I added a test that proves this decision. I also rejected suggestions to add a database, scheduled job, separate search endpoint, and saved views because they exceeded the sprint scope.

The Break Tests were the strongest proof that the new tests were meaningful. When I weakened date validation, the invalid-date test failed. When I disabled the search predicate, the title-search test returned an extra task and failed. After restoring the production code, the full suite returned green. This process reinforced the course principle that AI output is a draft: the useful result comes from clear constraints, diff inspection, running the app and tests, and making evidence-based decisions about what to accept, edit, or reject.
